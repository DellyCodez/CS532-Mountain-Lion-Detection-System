# Version Control Plan

## Project
Mountain Lion Detection System

## Purpose
The purpose of this version control plan is to explain how our team will manage project files, software versions, branches, and changes throughout development.

The goal is to keep the repository organized and make sure the team can identify the current version of the project as well as previous versions when needed.

## Version Control Tool
GitHub will be used as the version control system for the Mountain Lion Detection System.

The GitHub repository will be used to store and manage:

- Source code
- Requirements documentation
- Design documentation
- Test documentation
- Configuration management files
- Software versions and project history

## Repository
Repository Name:

CS532-Mountain-Lion-Detection-System

The repository will remain private and access will be limited to members of the project team.

## Main Branch
The `main` branch will contain the current approved version of the project.

Team members should avoid making unfinished development changes directly to the main branch.

The main branch should remain organized and contain work that is ready to be part of the project.

## Development Branches
Separate branches will be used when team members are working on new features or making changes.

Branch names should clearly describe the work being completed.

Examples may include:

- `alerts`
- `database`
- `user-interface`
- `reports`

Branch names may change depending on the actual components and tasks assigned during development.

## Pull Requests
When work on a branch is ready to be added to the main project, a pull request will be created.

Pull requests will allow the team to review changes before they are added to the main branch.

As Configuration Manager, I will keep track of pull requests and help make sure changes are being added to the correct version of the project.

## Change Control
Changes to software that is already part of the controlled project should be reviewed before the updated version is added back into the main project.

GitHub will provide a history of commits and changes so the team can see what was changed and when it was changed.

## Version History
Software versions will be maintained throughout the project.

GitHub commit history will be used to keep track of changes made during development.

Important versions of the project will be identified so the team can return to or review an earlier version if necessary.

## Baselines
Important approved versions of the project may be treated as project baselines.

These versions will represent important stages of development, such as an approved design, working software build, or final project release.

Baseline versions will be kept so they can be identified later if needed.

## Software Development Files
Software Development Folder information will be maintained as the project develops.

This information may include:

- Requirements associated with the software
- Source code identification
- Test information
- Peer review information
- Change history

## Build Information
As implementation begins, the team will keep track of information needed to build and run the software.

This may include:

- Development environment
- Software or tools required
- Build inputs
- Build procedure
- Build outputs
- Version information

## Configuration Manager Responsibilities
As Configuration Manager, my responsibilities for version control will include:

- Keeping the GitHub repository organized
- Managing the branch structure
- Keeping track of pull requests
- Helping maintain project versions
- Making sure important project files are stored in the repository
- Maintaining configuration management documentation
- Keeping track of important software baselines as the project develops
